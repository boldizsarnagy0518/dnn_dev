1. Bevezetés ­ Mi az a DotNetNuke?
A DotNetNuke, vagy röviden DNN, egy nyílt forráskódú tartalomkezel rendszer (CMS), amelyet a .NET platformon fejlesztettek ki, és amelyet elssorban vállalati, intézményi weboldalak üzemeltetésére használnak.
A DNN lényegében egy keretrendszer, amely lehetvé teszi, hogy a weboldal tartalmát, kinézetét és funkcionalitását modulok segítségével bvítsük. Minden funkció, legyen az hírlevél, eseménynaptár, fórum vagy bármi más, egy önálló, cserélhet darabként létezik az oldalon.
Miért fontos ez nekünk?
Amikor DNN-be fejlesztünk, nem egy hagyományos webalkalmazást írunk. Nem mi hozzuk létre az egész oldalt, hanem egyetlen, jól meghatárolt funkcióegységet, modult illesztünk bele egy már meglév rendszerbe.

A DNN hosszú éveken át WebForms-alapú modulokat (ASCX) támogatott, és sok régi rendszer ma is így mködik. Aztán a DNN 9.x-es verziójával megjelent az igazi MVC támogatás, ami lehetvé tette, hogy modern, tesztelhet, jól strukturált kódot írjunk.
2. MVC minta
Az MVC (Model-View-Controller) egy architekturális tervezési minta, amely a felelsségeket három elkülönül rétegre osztja:
· Model ­ az adatok és az üzleti logika reprezentációja · View ­ a megjelenítési réteg, amit a felhasználó lát · Controller ­ a logika, amely a kéréseket fogadja és koordinálja
Ha valaki már fejlesztett ASP.NET MVC alkalmazást, az MVC mködése ismers lesz. Ami viszont DNN-specifikus, az a módszer, ahogyan ez az egész befészkeli magát a CMS rendszerbe.
Hogyan fut le egy kérés DNN-ben?
Normál ASP.NET MVC esetén a folyamat egyszer: HTTP-kérés jön, a routing meghatározza a controllert és az actiont, az action visszaad egy View-t, és kész. DNN-ben ez kicsit összetettebb, mert a DNN saját routing és modul-felismer mechanizmusa is közbeszól.
Amikor egy DNN oldalon betöltdik egy MVC modul, a DNN framework megkeresi a megfelel controllert az URL-ben lév mid (Module ID) és a route adatok alapján. Egy tipikus DNN MVC URL valahogy így néz ki:
https://pelda-oldal.hu/TabId/42/ctl/MVC/mid/128/controller/Event/action/Index
Ez elsre meglep lehet, de lényegében ugyanaz történik, mint egy normál MVC alkalmazásnál ­ csak a DNN hozzáadja a saját kontextusát (melyik oldalon, melyik modulban vagyunk).
A DNN MVC Controller különlegessége
A leglényegesebb különbség az, hogy a DNN MVC controllerünk nem System.Web.Mvc.Controller-bl örökldik, hanem a DNN saját DnnController-ébl:
public class EventController : DnnController {
// ... }
A DnnController maga is Controller-bl örökldik, de rárakja a DNN-specifikus funkciókat, hozzáférést biztosít a portál kontextushoz, a modul beállításaihoz, a felhasználói jogosultságokhoz.

Mieltt egyetlen sor kódot írnánk, be kell állítanunk a fejleszti környezetet. Ez általában a következkbl áll:

DNN lokális telepítése
A DNN lokális telepítése önmagában egy hosszabb folyamat, amelyet most nem részletezünk. A lényeg: a fejlesztéshez szükségünk van egy futó DNN példányra, amelybe a modulunkat majd be tudjuk tölteni.
Visual Studio projekt sablon
A DNN Foundation biztosít egy projekt sablonkészletet (DNN Module Templates), amelyek letölthetk a Visual Studio Marketplace-rl. Ezek a sablonok automatikusan beállítják a fájlstruktúrát, az assembly hivatkozásokat és az alapvet konfigurációt.

5. Adatbázis tervezés és SQL scriptek

13. Tipikus hibák és tanulságok
Fejlesztés közben mindenki belefut bizonyos tipikus hibákba. Az alábbiakban összegyjtöttem a leggyakoribbakat, hogy elkerülhetk legyenek.
1. Fat Controller
Ez az egyik leggyakoribb hiba, fleg az új fejlesztk körében. A Controller elkezd egyre több logikát felvenni, amíg végül minden benne van, az adatbázis-hívástól az üzleti szabályokig.
Rossz:
public ActionResult Edit(EventViewModel viewModel) {
// Controller-be írt adatbázis-hívás ­ TILOS! string connStr = Config.GetConnectionString(); using (var conn = new SqlConnection(connStr)) {
conn.Open(); var cmd = new SqlCommand("INSERT INTO Events...", conn); cmd.ExecuteNonQuery(); }

return RedirectToDefaultRoute(); } Helyes: Az adatbázis-hívás a DataProvider-ben van, az üzleti logika a Service-ben. A Controller csak koordinál.
2. DBNull nem kezelése Ha egy nullable mez null érték az adatbázisban, és ezt nem kezeljük az IDataReader-ben, InvalidCastException-t kapunk futásidben. Rossz: Description = (string)reader["Description"] // Crash, ha Description NULL az adatbázisban Helyes: Description = reader["Description"] == DBNull.Value ? null : (string)reader["Description"] // vagy DNN helper segítségével: Description = Null.SetNullString(reader["Description"])
3. ModuleId hiánya lekérdezéseknél Egy DNN oldalon ugyanabból a modulból akár több példány is lehet. Ha nem szrünk ModuleId-ra, az összes modul az összes eseményt mutatja, nem azt, ami hozzá tartozik. Rossz: SELECT * FROM CampusEvents -- Minden rekord, minden modulból! Helyes: SELECT * FROM CampusEvents WHERE ModuleId = @ModuleId
4. Verziókövetés hiánya az SQL scriptekben Ha az adatbázist közvetlenül módosítjuk (nem script révén), az más fejleszti vagy tesztéles környezetben nem fog érvényesülni. Minden séma-módosítás egy új .SqlDataProvider fájlba kerüljön, a megfelel verziószámmal.

5. Körkörös függség a rétegek között
Ha a Service réteg importálja a Controller névteret, vagy a DataProvider importálja a Service névteret, az komoly architekturális hiba. A függségek mindig felülrl lefelé mutatnak:

16. Fájlfeltöltés és fájlkezelés DNN-ben
A fájlkezelés az egyik olyan terület, ahol a DNN saját rendszere lényegesen különbözik egy sima ASP.NET alkalmazástól. A DNN rendelkezik egy beépített fájlkezel szolgáltatással (IFileManager, IFolderManager), és ersen ajánlott ezt használni a nyers fájlrendszervagy adatbázis-mveletek helyett.
Miért a DNN saját fájlkezelje?
A DNN fájlrendszere portálonként szeparál, minden portálhoz saját médiakönyvtár tartozik, és a fájlok meta-adatai (fájlnév, méret, mime-type, tulajdonos) az adatbázisban is nyilván vannak tartva. Ezáltal: - Az adminisztrátor a DNN File Manager felületén is látja és kezelheti a feltöltött fájlokat - A fájlokhoz DNN-szint jogosultság rendelhet (ki láthatja, ki töltheti le) - A fájlok URL-je konzisztens és portálfügg

Admin letöltési API végpont
Ha az adminisztrátor egy külön API végponton keresztül is el szeretné érni a csatolmányokat (pl. egy listában, ahol minden esemény mellé letöltési link kell), bvíthetjük az EventApiController-t:
// GET /API/CampusEvents/EventApi/GetAttachmentUrl?eventId=7 [HttpGet] [DnnModuleAuthorize(AccessLevel = SecurityAccessLevel.Edit)] public HttpResponseMessage GetAttachmentUrl(int eventId) {
try {
var eventInfo = _eventService.GetEvent(eventId);
if (!eventInfo.AttachmentFileId.HasValue) {
return Request.CreateErrorResponse(HttpStatusCode.NotFound, "Nincs csatolmány ehhez az eseményhez.");
}
var fileService = new EventFileService(); string url = fileService.GetDownloadUrl(eventInfo.AttachmentFileId.Value);
return Request.CreateResponse(HttpStatusCode.OK, new { DownloadUrl = url });
} catch (ArgumentException ex) {
return Request.CreateErrorResponse(HttpStatusCode.NotFound, ex.Message);
} }
